# Промпт. Полировка Текущего Состояния

Ты работаешь в репозитории `goMH`. Целевая версия языка: `Go 1.25.1`.

Основной рефакторинг уже выполнен. Сейчас не нужно снова перестраивать архитектуру большими этапами. Нужно аккуратно довести текущий код до качественного и предсказуемого состояния, исправить оставшиеся шероховатости, выровнять UX и документацию, не ломая функциональность.

## Главная цель

Привести текущую реализацию к хорошему эксплуатационному виду:
- закрыть остаточные баги и несогласованности;
- привести поведение логирования и очереди в честный, предсказуемый формат;
- не потерять уже внедренную архитектуру;
- не расширять сильно область работ сверх текущих договоренностей.

## Жесткие ограничения

1. Не ломай существующую функциональность.
2. Не делай новую крупную архитектурную революцию.
3. Не реализуй сейчас полноценную сагу, компенсацию и откат по всем модулям.
4. GUI-режим пока не является целевой боевой поверхностью. Он остается тестовым фундаментом, поэтому не нужно тратить основную итерацию на его развитие, кроме случаев, когда надо поправить базовую согласованность кода.

## Зафиксированная позиция по отмене задач

Это важно и должно быть отражено в коде, UX и документации одинаково.

- Полноценная отмена задач требует паттерна саги и механизма компенсации для каждого модуля.
- На текущем этапе этого механизма нет.
- Поэтому сейчас отмена поддерживается только на этапе скачивания, где мы можем безопасно:
  - остановить загрузку;
  - удалить недокачанный файл;
  - корректно отразить это в статусе и логах.
- Все остальные задачи пока не отменяются.
- Нельзя показывать пользователю, что задача отменяема, если модуль/этап не поддерживает безопасный откат.

## Зафиксированная позиция по GUI

- GUI сейчас тестовый.
- Он нужен как фундамент для будущего развития.
- Не нужно искусственно доводить GUI до уровня TUI в этой итерации.
- Допустимы только правки, которые:
  - убирают архитектурную несогласованность;
  - упрощают поддержку;
  - не создают ложного впечатления, что GUI полностью готов.

## Что нужно сделать

1. Проверить и исправить логирование.
   Нужно убедиться, что отключение файлового логирования отключает только запись в файл, а не весь централизованный логгер.
   Если сейчас при `logging.file_enabled=false` весь `slog` уходит в пустоту, это нужно исправить.
   Нужен внятный fallback, например консольный или другой согласованный sink.

2. Привести runtime очереди к честной модели отмены.
   Если задача не поддерживает безопасную отмену, queue/runtime/UI не должны маркировать ее как cancelable.
   Отмена должна быть доступна только там, где она действительно корректно реализована.
   На текущем этапе это касается скачивания и связанных с ним операций.

3. Проверить UX вокруг отмены и статусов.
   Тексты в TUI, queue runtime и логах должны явно соответствовать реальному поведению.
   Нельзя оставлять формулировки, которые обещают общую отмену задач, если по факту она работает только на скачивании.

4. Довести `main` и базовый runtime до аккуратного формата.
   Нужно убрать все оставшиеся шероховатости, где завершение процесса или cleanup идут не самым аккуратным путем.
   Если есть места, которые обходят основной путь завершения и мешают нормальному освобождению ресурсов, их нужно привести в порядок.

5. Проверить остаточные технические долги после рефакторинга.
   Нужно убрать мелкие дубли, неиспользуемые адаптеры, неаккуратные временные решения, которые уже не нужны.
   Но не нужно снова переписывать полпроекта ради косметики.

6. Актуализировать документацию.
   Нужно обновить документы в `docs/refactor-plan`, если они перестали соответствовать реальному состоянию.
   Особенно важно зафиксировать:
   - текущее поведение логирования;
   - реальные границы отмены задач;
   - тестовый статус GUI;
   - оставшиеся сознательные ограничения.

## На что обратить особое внимание в коде

- `logging/logging.go`
- `main.go`
- `taskqueue/queue.go`
- `app/modruntime/*`
- `app/consolequeue/*`
- `modules/serviceutils/serviceutils.go`
- места, где очередь/интерфейс помечают задачу как отменяемую
- места, где еще остались misleading UX-сообщения

## Что не нужно делать

- Не внедряй полноценную сагу.
- Не делай универсальный rollback для модулей.
- Не расширяй GUI до полноценного боевого режима.
- Не изобретай новую архитектуру модулей поверх уже внедренной.

## Критерии готовности

- Отключение файлового логирования не выключает весь общий логгер.
- Очередь честно отражает текущие реальные возможности отмены.
- Отмена задач доступна только там, где безопасно поддерживается.
- Тексты UX и статусы не вводят в заблуждение.
- Код остается совместимым с текущей архитектурой.
- `go test ./...` проходит.
- `go vet ./...` проходит.

## Что показать в отчете

- Какие именно проблемы текущего состояния исправлены.
- Как теперь работает логирование при `logging.file_enabled=false`.
- Как теперь отражается отменяемость задач и где именно она доступна.
- Какие документы обновлены.
- Какие ограничения сознательно оставлены на следующий этап.
